Framework Engineering Highlights

⚡

ThreadLocal Driver Sandbox Isolation

Ensures absolute thread safety during high-concurrency parallel runs. Playwright BrowserContext, Page, and Playwright instances are completely isolated per execution thread to eliminate collisions and cross-session contamination.

🧩

Clean Page Object Model & Page Component Patterns

Selectors and UI action methods are encapsulated strictly inside Page Objects. Complex repeating sections (e.g. navigation headers, side bars, data tables) are abstracted into modular Page Components, encouraging massive code reusability.

🔌

Dual-Purpose Hybrid Testing (RestAssured Sync)

Combines RestAssured API calls directly inside UI test lifecycles to pre-seed database conditions, bypass lengthy onboarding screens, and perform instant state assertions, accelerating UI test runs up to 300%.

Q1. What is the difference between Playwright and Cypress?
Playwright supports all major browsers (Chromium, Firefox, WebKit) including cross-browser in a single run, runs tests out-of-process for true multi-tab/multi-origin testing, and supports multiple languages (JS, Java, Python, C#). Cypress is JS-only, runs inside the browser making it faster for single-origin tests but limiting for multi-tab or multi-domain flows. Playwright's auto-wait is built into every action; Cypress uses retryable commands with a fixed timeout chain.
Q2. How do you implement the Page Object Model (POM) in Playwright with JavaScript?
Create a class per page, inject `page` via constructor, expose typed action methods and assertion methods. Locators are defined as class properties using `page.locator()`. Tests import the page class and call its methods — never access locators directly from the test. This keeps selectors in one place and tests readable.
Q3. Explain Playwright's auto-waiting mechanism.
Before every action (click, fill, etc.), Playwright waits for the target element to be: attached to DOM, visible, stable (not animating), enabled, and ready to receive events. This eliminates manual `waitForSelector` in most cases. For navigation-heavy flows use `waitForLoadState('networkidle')` or `waitForURL()`.
Q4. How do you handle iframes in Playwright?
Use `page.frameLocator('iframe-selector')` to get a FrameLocator, then chain locators on it exactly like on the main page. For dynamically created iframes, use `page.waitForSelector('iframe')` first, then `page.frame({ url: /pattern/ })` or `page.frames()` to locate by URL or name.
Q5. How do you run Playwright tests in parallel and control worker count?
In `playwright.config.js`, set `workers: N` (e.g., `workers: 4`) or `workers: '50%'` for half the CPU cores. Each worker is an isolated browser context. Tests within a spec file run serially by default; use `test.describe.parallel()` for intra-file parallelism. Ensure tests are stateless — no shared login state without `storageState`.
Q6. How do you handle dynamic elements or flaky locators in Playwright?
Prefer semantic locators: `getByRole()`, `getByLabel()`, `getByText()` over CSS/XPath. For dynamic IDs, use `data-testid` attributes. Use `locator.filter()` to narrow down a list. For race conditions, use `page.waitForResponse()` or `page.waitForSelector()` instead of fixed sleeps.
Q7. How do you capture screenshots and traces on failure in Playwright?
In `playwright.config.js`: set `screenshot: 'only-on-failure'`, `video: 'retain-on-failure'`, `trace: 'on-first-retry'`. On failure, run `npx playwright show-trace trace.zip` to replay the full timeline of actions, DOM snapshots, and network calls.
Q8. What is Cypress's intercept feature and what's its Playwright equivalent?
Cypress `cy.intercept()` stubs or spies on network requests. In Playwright, use `page.route('**/api/endpoint', route => route.fulfill({ json: mockData }))` to mock, or `page.waitForResponse('**/api/**')` to assert a real response. Playwright routes are more flexible — they support aborting, modifying, and continuing requests.

Q9. How do you validate JSON schema in REST Assured?
Use `.body(matchesJsonSchemaInClasspath("schema.json"))` from the `rest-assured-json-schema-validator` dependency. The JSON Schema file (draft-04 or draft-07) defines required fields, types, and constraints. This catches contract breaks even if individual field assertions pass.
Q10. How do you handle OAuth 2.0 token-based auth in REST Assured?
Make a POST to the token endpoint with client credentials/password grant, extract the `access_token` from the response, then pass it as a Bearer header: `.header("Authorization", "Bearer " + token)`. Cache the token per test class using `@BeforeClass` and refresh when a 401 is returned.
Q11. What is Postman's Collection Runner and how do you use it in CI?
Collection Runner runs a saved collection in sequence with environment variables and data files. For CI, export the collection and environment JSON, then run via Newman: `newman run collection.json -e env.json --reporters junit` which outputs JUnit XML for Jenkins to parse.
Q12. How do you chain API requests (use response of one as input to the next) in REST Assured?
Extract the value: `String id = given().post("/create").then().extract().path("id");`. Then inject: `given().pathParam("id", id).get("/item/{id}")`. For Postman, use `pm.environment.set("id", pm.response.json().id)` in the Tests tab of request 1, then reference `{{id}}` in request 2.
Q13. How do you test negative/error scenarios in API automation?
Send requests with: missing required fields, invalid data types, out-of-range values, expired tokens, duplicate payloads, and injection payloads. Assert correct HTTP status codes (400, 401, 403, 422) and validate the error response body schema matches the documented contract.

🎯 Scenario Q15. API returns paginated data — how do you fetch all pages in REST Assured and assert total count?
List<Map<String, Object>> allRecords = new ArrayList<>();
int page = 1;
boolean hasMore = true;

while (hasMore) {
  Response resp = given()
    .queryParam("page", page)
    .queryParam("size", 50)
    .header("Authorization", "Bearer " + getToken())
    .get("/api/courses");

  List<Map<String, Object>> items = resp.jsonPath().getList("data");
  allRecords.addAll(items);
  hasMore = resp.jsonPath().getBoolean("pagination.hasNextPage");
  page++;
}

// Assert total matches API-reported count
int totalReported = given().get("/api/courses/count").then().extract().path("total");
Assert.assertEquals(allRecords.size(), totalReported, "Paginated total mismatch");
🎯 Scenario Q16. Test rate limiting: assert the API returns 429 after 5 rapid identical requests in REST Assured.
@Test
public void apiReturns429AfterRateLimit() {
  String endpoint = "/api/search";
  String body = "{\"q\":\"playwright\"}";
  int hitCount = 0;

  for (int i = 0; i < 6; i++) {
    Response resp = given()
      .contentType(ContentType.JSON)
      .body(body)
      .post(endpoint);

    if (resp.statusCode() == 429) {
      hitCount++;
      // Assert the Retry-After header is present
      Assert.assertNotNull(resp.getHeader("Retry-After"), "Retry-After header missing");
      break;
    }
  }
  Assert.assertTrue(hitCount > 0, "Rate limit (429) never triggered in 6 calls");
}
Q14. How do you verify data integrity after an API call using SQL?
After calling the POST/PUT API, query the database directly: `SELECT * FROM orders WHERE order_id = ?` using the ID returned in the API response. Assert that every field persisted correctly — amounts, statuses, timestamps, foreign keys. This catches cases where the API returns 200 but the write silently fails or truncates data.
Q15. Write a query to find duplicate email records in a users table.
SELECT email, COUNT(*) AS cnt
FROM users
GROUP BY email
HAVING COUNT(*) > 1;
To see the full rows: wrap with a JOIN back to the table on email. Use this as a pre-test data-quality check to avoid false positives from dirty test data.
Q16. What is the difference between INNER JOIN, LEFT JOIN, and FULL OUTER JOIN?
INNER JOIN returns only matching rows from both tables. LEFT JOIN returns all rows from the left table and matched rows from the right (nulls where no match). FULL OUTER JOIN returns all rows from both tables, nulls on unmatched sides. For QA: LEFT JOIN is useful to find orphan records (right side is NULL means missing reference).
Q17. How do you handle test data setup and teardown with SQL in automation?
Use `@BeforeEach`: INSERT test-specific rows with unique IDs (UUID or timestamp-prefixed). Use `@AfterEach`: DELETE WHERE id IN (collected IDs) or use transactions rolled back after each test. Never rely on pre-existing data in a shared DB — tests must be self-contained and order-independent.
Q18. What is the difference between `==` and `===` in JavaScript?
`==` performs type coercion (`"5" == 5` is true). `===` is strict equality — no coercion (`"5" === 5` is false). In test assertions always use `===` or framework matchers (Jest's `toBe`, Playwright's `expect`) to avoid false positives from coercion.
Q19. Explain Promises vs async/await and how they apply to Playwright tests.
Promises are objects representing eventual values. `async/await` is syntactic sugar that makes asynchronous code look synchronous, making it easier to read and debug. All Playwright actions return Promises, so every action must be `await`-ed in an `async` test function. Forgetting `await` means the action is never executed — the test passes vacuously.
Q20. How do TypeScript interfaces help in Playwright POM?
Define interfaces for test data (`interface LoginData { username: string; password: string; }`) and page return types. TypeScript catches typos at compile time, enforces data shapes in data-driven tests, and makes refactoring safe — rename a property and the compiler shows every broken reference.
Q21. What is a closure and how can it cause issues in test automation?
A closure is a function that captures variables from its surrounding scope. In test loops, closures capturing `let i` or `let item` in an `async` callback may capture stale references if the iteration variable changes before the async completes. Fix with `for...of` loops (each iteration has its own binding) or destructuring inside the loop body.
Q22. How do you integrate Playwright tests into a Jenkins pipeline?
In your `Jenkinsfile`: (1) `npm ci` to install deps, (2) `npx playwright install --with-deps` to install browsers, (3) `npx playwright test --reporter=junit` to run and output JUnit XML, (4) use `junit 'test-results/*.xml'` to publish results, (5) `archiveArtifacts 'playwright-report/**'` for the HTML report.
Q23. How do you run tests in parallel across Jenkins agents?
Use Jenkins `parallel` step in a declarative pipeline to split test suites across multiple agents (each running a subset of specs). Alternatively, use Playwright's built-in `--shard=1/4` flag: four Jenkins jobs each run one shard, merge the `.last-run.json` files for unified reporting.
Q24. How do you handle environment-specific configs in Jenkins for test runs?
Use Jenkins environment variables or credentials store for secrets. In Playwright config, read `process.env.BASE_URL`, `process.env.ENV` etc. Pass them at run time: `BASE_URL=https://staging.app.com npx playwright test`. Never hardcode URLs or credentials in the test code or commit `.env` files.
Q25. Explain your approach to release validation in CI/CD.
Run smoke suite (critical-path tests, ~5-10 min) on every PR merge. Run full regression suite nightly. Gate releases on smoke suite pass. On failure: build is marked unstable, team is notified via Slack webhook. Maintain a "release readiness dashboard" aggregating smoke, regression, and API test results with trend graphs.
Q26. How have you used GenAI tools to accelerate QA activities?
I use GitHub Copilot to generate Playwright boilerplate (POM classes, fixture setups) and suggest assertions. For test case generation, I prompt an LLM with the user story + acceptance criteria to get an initial test case matrix, then review and prune. For defect analysis, I paste stack traces into the chat to get root cause hypotheses faster. This cuts initial drafting time by ~40%.
Q27. What are the risks of relying on AI-generated test cases?
AI may miss domain-specific edge cases, generate redundant tests, or hallucinate incorrect assertions. It has no knowledge of your actual system behavior. Mitigation: use AI output as a first draft only, always review against requirements, run generated tests to confirm they fail correctly before trusting them as valid coverage.
Q28. How do you use AI for defect analysis beyond just "copying the error message"?
Provide full context: stack trace + recent code diff + test scenario + environment details. Ask the AI to identify the root cause pattern (not just symptoms), suggest the minimal reproduction case, and list similar historical bugs to check. Then validate the AI's hypothesis by manual reproduction before filing the bug report.
Q29. Walk me through your STLC process for a new feature.
Requirement Analysis → Test Planning (scope, timelines, tools, risks) → Test Case Design (boundary values, equivalence partitioning, decision tables) → Test Environment Setup → Test Execution (smoke first, then functional, then regression) → Defect Reporting & Re-testing → Test Closure (metrics: pass%, defect density, automation coverage).
Q30. How do you onboard a new automation engineer to your framework?
Week 1: framework architecture walkthrough (layers, conventions, how to run tests locally). Week 2: assign a small feature to automate end-to-end with a buddy reviewer. Week 3: independent contribution with PR review. Document "framework guide" in the repo wiki covering: setup, naming conventions, how to add a new POM, how to run subsets via tags, and how to read trace reports.
Basic XPath Patterns
XPath Find a button containing the text "Submit"
// XPath
//button[contains(text(),'Submit')]

// Playwright equivalent (always prefer this)
page.getByRole('button', { name: 'Submit' })

// XPath with normalize-space (handles extra whitespace)
//button[normalize-space()='Submit']
XPath Find an input field by its placeholder text
// XPath
//input[@placeholder='Enter your email']

// Playwright
page.getByPlaceholder('Enter your email')

// Partial placeholder match
//input[contains(@placeholder,'email')]
XPath Find the 3rd row in a data table
// XPath - absolute position
//table/tbody/tr[3]

// XPath - nth child
//tbody/tr[position()=3]

// Playwright
page.locator('table tbody tr').nth(2)  // 0-indexed

// Get text of 2nd cell in 3rd row
page.locator('table tbody tr:nth-child(3) td:nth-child(2)')
XPath Find a label's associated input using for/id relationship
// Get the input whose id matches a label's "for" attribute
//input[@id=//label[text()='Username']/@for]

// Playwright (cleanest — traverses for/id automatically)
page.getByLabel('Username')

// CSS equivalent
label:has-text("Username") + input
// or
input#username
Intermediate — Axes & Relationships
XPath Find a sibling element — click "Edit" button next to the row containing "Alice"
// following-sibling axis
//tr[td[text()='Alice']]//button[text()='Edit']

// Or using contains for partial match
//tr[td[contains(text(),'Alice')]]/td//button[@data-action='edit']

// Playwright filter approach (much more readable)
page.locator('tr').filter({ hasText: 'Alice' }).getByRole('button', { name: 'Edit' })
XPath Find a parent element from a child — navigate up from an error message to its form
// ancestor axis — go up to form from error span
//span[@class='error-msg'][text()='Required']/ancestor::form

// parent axis — go up one level
//span[@class='error-msg']/parent::div

// Playwright — locator chaining (no XPath needed)
page.locator('form').filter({ has: page.locator('.error-msg') })
XPath Find an element by multiple attributes (AND condition)
// AND: button that is both type=submit AND has class=primary
//button[@type='submit' and contains(@class,'primary')]

// OR: input that is either email or text type
//input[@type='email' or @type='text']

// NOT: all inputs except hidden
//input[not(@type='hidden')]

// CSS equivalent of AND
button[type="submit"].primary
Advanced — Dynamic IDs & React/Angular
XPath Element has dynamic ID like "btn-12345-submit". How do you locate it?
// starts-with for prefix pattern
//button[starts-with(@id,'btn-') and contains(@id,'-submit')]

// Better: use data-testid (negotiate with dev to add it)
//button[@data-testid='submit-btn']

// Playwright — semantic locators avoid dynamic ID problem entirely
page.getByRole('button', { name: 'Submit' })
page.getByTestId('submit-btn')  // uses data-testid attribute
XPath Find the last item in a list dynamically
// last() function
//ul[@class='course-list']/li[last()]

// second to last
//ul[@class='course-list']/li[last()-1]

// Playwright
page.locator('.course-list li').last()
page.locator('.course-list li').nth(-1)  // negative index = from end
XPath Locate elements inside a Shadow DOM — what breaks and how do you fix it?
XPath cannot pierce Shadow DOM boundaries — it stops at the shadow root and returns nothing. Solutions: 
// Playwright — automatically pierces open shadow roots
page.locator('my-component >> button[type="submit"]')
// or chain locators
page.locator('my-component').locator('button[type="submit"]')

// For closed shadow DOM: inject script
await page.evaluate(() => {
  const host = document.querySelector('my-component');
  return host.shadowRoot.querySelector('button').click();
});

C3. Write a SQL query to find the 2nd highest salary from an employees table.
SELECT MAX(salary) AS second_highest
FROM employees
WHERE salary < (SELECT MAX(salary) FROM employees);

-- Or using DENSE_RANK for top-N generalization:
SELECT salary FROM (

Q1. What is Playwright and how does it differ from Selenium?
Playwright is async-first, supports Chromium/Firefox/WebKit, has built-in auto-wait on every action, native network interception, and isolated browser contexts for parallelism. Selenium needs explicit waits, has no built-in API layer. Playwright's single fixture covers both UI and API testing via the request fixture — no extra library needed.
Q2. Explain Playwright auto-waiting and how it prevents flakiness.
Before every actionable call (click, fill, check) Playwright checks the element is: attached, visible, stable (not animating), enabled, editable. No Thread.sleep needed. For navigation use waitForURL() or waitForLoadState('networkidle'). Custom waits: expect(locator).toBeVisible() retries until timeout.
